## Item 8: the plan hash and the Python

- **New value `fedec49c14f3eafd`**, the same on 3.14 32-bit and 3.12 64-bit. Written by `py tools/levels/forest.py
  build` (3.14) into `src/shared/Config/LevelDress/ForestRoad.json` and the bake record, and into Assets.json through
  `assets_config.load_assets()` / `save_assets()` (a one-line diff). `py tools/assets/upload_level.py --level ForestRoad
  --dry-run`: **0 upload(s) pending** (5 images and 37 meshes already uploaded and unchanged). `forest.py check`: PASS
  under `py` and under `py -3.12`; `forest.py mutants`: 29/29 caught (3.14).
- **Cause.** `plan_hash` hashed every kit piece's `kit.glb_bytes`. The two Pythons' math differs in the last bit (666 of
  45,567 kit corners, by at most 1.8e-15 studs; no corner's float32 moves), but a GLB's flat normals are computed from
  the corners, and on a face that should lie on an axis a normal component of about 1e-16 on one Python is exactly 0 on
  the other. Seven pieces' GLBs differed (Banner, ChiefTent, HideTent, LogSeat, Mushrooms, Watchtower, WeaponRack), in
  NORMAL data only. Not float formatting, rounding or dict order: the JSON parts hash the same.
- **Fix (`tools/levels/forest.py`).** `kit_geometry(mesh)`: each triangle's corners as float32 (what the GLB stores) and
  its colour, in order; the normals carry nothing the corners do not. A corner whose float32 would move within
  `KIT_ULP_SLACK` (16) ulps of its float64 raises a ValueError naming the piece, so the hash cannot silently become
  Python-dependent again (proved on a scratch corner at 1 + 2^-24: refused). Today's value could not be kept: it was a
  hash of 3.14's normals.
- **Writes, proved first.** A scratch 3.14 bake differed from the shipped one only by the 16 digits (every GLB, the
  palette, the bake record's sha256s, `bake.json` and the dress file byte-identical otherwise); then the in-place build
  rewrote the GLBs byte-identical.
- **Left, for the lead:** the baked level GLBs' own bytes still depend on the Python the same way: a 3.12 bake differs in
  `Cover`, `Hills_1` and `Dress_11` (normals only, components of 1e-14 or less), so a re-bake under 3.12 would re-upload
  those three meshes with the same look. Bake under `py` (3.14), as the shipped meshes were. The cure (snap normal
  components under 1e-9 to 0 in `levelmesh` and `forest_kit`'s writers) changes the shipped 3.14 bytes too, so it
  belongs to the next re-bake that re-uploads anyway.
- **docs-keeper:** `docs/ASSET_MANIFEST.md` still prints `23851a6f417491c1`; `py tools/gen_asset_manifest.py` rewrites it.
